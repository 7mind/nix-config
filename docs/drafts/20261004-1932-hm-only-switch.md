# Home Manager-only switch on NixOS

Status: implemented in the configuration. A full NixOS switch must install the integration before the first persistent Home Manager-only switch.

## Goal

Apply a Home Manager change without `switch-to-configuration`: no bootloader update, no system-unit restarts, no full `/etc` rewrite. Packages must stay visible inside the yolo sandbox.

## Previous integration

Home Manager is a NixOS submodule with `home-manager.useUserPackages = true`.

- `home-manager-<user>.service` is part of the system closure. `ExecStart` is a store path of that generation's activation package, and the unit is `WantedBy=multi-user.target`. Every boot re-applies that generation.
- `/etc/profiles/per-user/<user>` is an `environment.etc` entry: a symlink in `/etc` to `/etc/static/profiles/per-user/<user>`, which is a `buildEnv` of `users.users.<user>.packages` (including `home.path`). etc activation rewrites it from the booted generation.

An out-of-band `activate` updates files under `$HOME` only. The next boot runs the old unit and writes the old files back. Packages never move, because with `useUserPackages = true` the activation script does not install them.

## Why `useUserPackages = false` is not the fix

That flag makes activation `nix-env -i` `home.path` into the default user profile (`~/.local/state/nix/profile` when `use-xdg-base-directories` is set; `~/.nix-profile` otherwise). NixOS `PATH` searches those directories before `/etc/profiles/per-user/$USER`.

yolo execs bare `codex` / `claude` / `pi` inside bubblewrap. It bind-mounts `/etc`, `/nix/store`, and `/nix/var`, not `$HOME`. A profile path under `$HOME` does not exist in the sandbox even when its target is in the store. `/etc/profiles/per-user/$USER` works because the symlink lives under `/etc`. After the flag flip, that directory no longer contains the Home Manager binaries, so the harness lookup fails.

The same flag also does not survive reboot: the system unit still re-runs the generation baked into the closure, and that activation reinstalls that generation's `home.path`.

## Implemented design

One host switch installs the integration. After that, Home Manager-only applies do not call `switch-to-configuration`.

1. Keep `useUserPackages = true`. Do not install into the default user nix profile, and do not create `~/.nix-profile`.
2. Keep the selected generation in `/nix/var/nix/profiles/smind-home/$USER/generation`. Point `/etc/profiles/per-user/$USER` at its `home-path`. One profile selection therefore controls both activation and package visibility. Other `users.users.<user>.packages` remain available through `/etc/profiles/per-user-system/$USER`. `/etc` and `/nix/var` are mounted in the sandbox, so existing `PATH` entries keep resolving.
3. Change `home-manager-<user>.service` so `ExecStart` runs the current profile's `activate`, not a store path from the system closure. Boot then follows the last Home Manager switch.
4. Home Manager-only apply: build the standalone activation package, select its NixOS activation variant with `nix-env --profile … --set`, and run `activate --driver-version 1`. This variant uses external package installation and does not install packages into the default user profile.
5. Serialize selection and activation with a per-profile lock. If activation fails, return its exit status and leave the candidate generation selected. Activation is not transactional: partial changes can remain, and a reboot into the same system retries the selected generation.

A full host switch must `--set` those same profiles from the generation being switched to. Otherwise a later host switch and a Home Manager-only switch diverge, and a rollback would not roll Home Manager back.

The system activation script creates a root-owned request recording the system generation, activation action, and bundled HM generation. The HM service processes it as the target user after the Nix daemon socket is available. Rebooting the same system preserves the selection; booting a different system generation selects its bundled HM generation. An explicit system switch creates a new request and restarts the HM service, selecting the bundled generation once. Later service restarts preserve subsequent HM-only switches. Root does not mutate profiles inside user-owned directories.

## Build isolation

Home Manager-only builds evaluate `homeConfigurations`, using explicit host contexts and the general package overlays. They do not evaluate or build `nixosConfigurations`.

## Usage

On the target NixOS host, first install the integration with a full switch, then apply home changes independently:

```bash
./setup -s
./setup --hm-only -s
```

Standalone Linux and Darwin installations use the usual user-profile activation.

## Verification

`python3 tests/home-manager-persistence-test.py` builds minimal real Home Manager generations and runs the same HM switch, boot-request selection, service restart, system switch, system rollback, and failed activation checks with dummy profile commands and real temporary Nix profiles. A failure after linking files must return its exit status, retain the candidate profile, and retry that candidate on a same-system boot request. It also checks the activation package's switch entry point and the prerequisite failure. Configuration assertions check boot-service and package-profile wiring. Boot requests are simulated; these checks do not reboot a VM or activate a live NixOS host.
